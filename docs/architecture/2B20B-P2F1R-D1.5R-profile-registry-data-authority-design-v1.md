This design supersedes only the D1.5P mechanism that parsed and rendered the
approved registry as verifier source text. Compatible D1.5/D1.5P/D1.5E
contracts remain frozen: one controlled S capture, direct `S -> P -> E`
ancestry, P artifact authority, E evidence-only custody, no self-reference,
unchanged product/tests/rules, and no D2 or publication.

## 2. Bounded outcome and non-goals

The outcome is one side-effect-free data module, a verifier that consumes it
directly, zero source-parser path, 17 preserved historical profile artifacts at
S, one appended profile artifact and record at P, one exact selector, and the
existing bounded E archive.

Non-goals are production or Vitest test edits; test-title or identity changes;
A/B/C/C1, event, semantic-validator, role-matrix, or BOTC-rule changes; a new
workflow/job/matrix; Hosted CI; push; PR; merge; D2; dynamic registration;
generic migration/profile/publication frameworks; `latest`; fallback; source
parsing; a second registry file; or a new permanent CLI/verifier.

## 3. Exact module and purity contract

The sole permanent new data-authority file is exactly:

```text
scripts/coverage-profile-registry.mjs
```

It is UTF-8, LF-only, no BOM, and exactly one terminal LF. It imports nothing
and performs no I/O, Git operation, environment read, process access, coverage
execution, mutation, registration, callback, inference, or filesystem action.
Its top level contains only constants, immutable literal data, `Object.freeze`
wrappers, and named exports.

The exact named exports are:

```text
COVERAGE_PROFILE_REGISTRY_SCHEMA_VERSION
COVERAGE_PROFILE_LIFECYCLE_STATUSES
COVERAGE_PROFILE_ARTIFACTS
COVERAGE_PROFILE_RECORDS
COVERAGE_PROFILE_SELECTORS
```

`COVERAGE_PROFILE_ARTIFACTS` holds the complete existing approved-profile
contract objects. These objects contain topology and obligation counts/hashes,
not raw coverage output. `COVERAGE_PROFILE_RECORDS` contains metadata only and
references an artifact by `profileArtifactId`; it never copies the artifact's
complete topology or obligations. Both tables live in the one module to avoid
a second registry/data file, while their authority roles remain distinct.

No mutation API is exported. Every array, record, nested delta, topology,
obligation, and selector value is recursively frozen.

## 4. Three authority boundaries

### 4.1 Profile Artifact Authority

P's `COVERAGE_PROFILE_ARTIFACTS` member is the actual approved coverage-profile
artifact. It owns `id`, `sourceHead`, `sourceKind`, topology, and obligations.
The new member is derived from the one complete S capture. Existing artifact
objects retain their exact ordered fields, values, whitespace spans, and
semantics when moved from the verifier into the module; P does not edit them.

The old 2930-byte/SHA fact remains archived evidence for the selected 2B20A
artifact. It is not recomputed by scanning source and is not a runtime verdict
input. New artifact identity uses SHA-256 of canonical profile-artifact JSON
data produced by the S materializer, never SHA-256 of JavaScript source text.

### 4.2 Registry Metadata Authority

`COVERAGE_PROFILE_RECORDS` owns lifecycle, provenance/count bindings,
artifact identity, and append order. `COVERAGE_PROFILE_SELECTORS` owns the one
explicit CI selector mapping. The metadata table cannot change artifact
obligations and cannot make an unmaterialized candidate accepted.

### 4.3 Evidence Authority

E owns only archived evidence that binds existing S/P/artifact data. E cannot
change the module, verifier, selector, workflow, artifact, product, or tests,
and it contains neither its own OID nor a future review result.

## 5. Closed metadata schema

The schema version is exactly:

```text
botc-coverage-profile-registry-v1
```

Each metadata record has exactly these ordered keys:

```text
schemaVersion
profileId
lifecycleStatus
sourceHead
sourceCount
testIdentityCount
inventorySha256
tupleSha256
profileArtifactId
profileArtifactSha256
logicalGroupCount
physicalGroupCount
previousProfileId
sourceDelta
testDelta
unexplainedLoss
```

The only lifecycle values are:

```text
HISTORICAL_ACCEPTED
ACTIVE
```

`sourceDelta` and `testDelta` are either `null` or frozen exact-key objects
`{ added, removed }`. Counts are non-negative safe integers. OIDs are lowercase
40-hex; SHA-256 values are lowercase 64-hex. `previousProfileId` is `null` or
an existing earlier profile ID. `profileArtifactId` must resolve to exactly one
artifact whose `id` and `sourceHead` equal the record values.

Historical contracts did not record every modern binding. A historically
unavailable `testIdentityCount`, `inventorySha256`, `tupleSha256`,
`profileArtifactSha256`, logical/physical count, delta, or loss value is
represented by `null`, never invented or inferred. A null means
`UNAVAILABLE_NOT_PASS`; it is not evidence of zero or success. Every `ACTIVE`
record must have non-null values for all fields except `previousProfileId` when
there is no predecessor. Every profile created at or after D1.5R must be fully
populated and may not use null for a capture binding.

At S there are exactly 17 records and 17 artifact objects in their immutable
existing append order. Sixteen records are `HISTORICAL_ACCEPTED`; the exact
2B20A record is `ACTIVE`. At P there are exactly 18 records and 18 artifact
objects: the 2B20A metadata status becomes `HISTORICAL_ACCEPTED`, the new record
is appended as the sole `ACTIVE` record, and no historical artifact bytes are
changed.

The new P profile/artifact/record ID is exactly:

```text
phase-3-slice-2b20b-p2f1r-d1-5r-<first7(actual-S)>-routing-coverage-v1
```

`<first7(actual-S)>` is evaluated only after S exists. The full `sourceHead`
field is actual S's lowercase 40-hex OID. The design does not predict either
value.

## 6. Selector schema and no-fallback contract

`COVERAGE_PROFILE_SELECTORS` is a dense array in raw UTF-16/code-unit ordinal
`selectorId` order. It contains exactly one frozen record with exact keys:

```text
schemaVersion
selectorId
profileId
```

The selector ID is exactly `CI_COVERAGE_PROFILE`. Its `profileId` must resolve
to the sole `ACTIVE` metadata record and exactly one artifact. At S it resolves
to `phase-3-slice-2b20a-4d576e2-final-restoration-v1`; P changes it to the
exact section 5 D1.5R profile ID using actual S.

The workflow continues to pass one literal `--profile` value and must equal the
registry mapping. A coverage-acceptance invocation without an exact profile ID
does not pass. Unknown, duplicate, inactive, prefix, partial, case-folded,
environment-selected, inferred, `latest`, or uniquely-matching-candidate
selection rejects. Non-selector baseline-comparison reporting may remain, but
it cannot produce an approved-profile acceptance verdict.

## 7. Registry validation and data quality

The verifier imports the five exports directly and validates values, not module
source. Validation order is:

1. schema/version and export presence;
2. dense arrays, recursive immutability, exact keys and key order;
3. deterministic historical append order;
4. profile-ID and artifact-ID uniqueness;
5. lifecycle/status domain and exactly one active record;
6. OID, SHA, count, nullability, delta, and loss domains;
7. record-to-artifact referential integrity;
8. metadata-to-artifact source/count/topology/tuple agreement where available;
9. selector uniqueness and exact active-record resolution;
10. requested exact selector/profile agreement;
11. actual inventory, tuple, counts, deltas, and obligation comparison.

Data-quality contract:

| Dimension | Frozen rule |
|---|---|
| Grain | One metadata record per `profileId`; one artifact per artifact `id`; one selector record per `selectorId` |
| Uniqueness | Duplicate profile, artifact, or selector IDs reject before comparison |
| Completeness | Every post-D1.5R record is fully populated; historical unavailable values are explicit null and cannot pass an active gate |
| Validity | Closed keys, status domain, safe counts, lowercase OID/SHA, non-negative deltas/loss, immutable dense arrays |
| Integrity | Metadata points to exactly one artifact; active selector points to exactly one active record; artifact and metadata source/count/topology/tuple fields agree |
| Reproducibility | source/test/group counts come from the canonical capture manifest; inventory SHA from canonical inventory bytes; tuple SHA from canonical tuple-census bytes; artifact SHA from canonical profile-artifact JSON bytes |

Future P/E values unavailable at S remain absent from the registry and pending
in documentation. They are never represented as `PASS`, zero, a predicted SHA,
or a placeholder record.

## 8. Verifier consumption model

`scripts/verify-coverage-obligations.mjs` imports the module directly. It may
validate and compare imported objects, canonical JSON data, coverage maps,
inventory, tuple data, counts, deltas, and obligations. It must not:

- read its own source or registry-module source;
- run `git show` to recover a profile span;
- search a marker, sentinel, suffix, close, or tail;
- calculate a fixed source offset or extract a source span;
- hash JavaScript source as profile authority;
- constrain a later top-level declaration;
- retain a diagnostic, compatibility, dual-read, or fallback parser path.

The terminal static census is exact:

```text
sourceTextScanSymbols=0
markerSentinelSymbols=0
tailSearches=0
sourceSpanExtractors=0
sourceParserBranches=0
registryMutationApis=0
fallbackSelectors=0
```

The existing stable coverage-map and obligation validators remain. Only their
profile data source and selector authority change.

## 10. Coverage and P boundary

After the S review gate, exactly one complete controlled S capture may produce
the actual artifact/candidate. The inherited single recorded infrastructure
retry boundary remains; semantic or deterministic failure has no retry.

The expected capture contract remains 69 sources, 1712 identities, source
delta `+6/-0`, test delta `+140/-0`, 11 logical coverage groups, 12 physical
coverage groups, tuple classification `62 unchanged / 1 changed / 6 added /
0 removed`, and zero missing, unexpected, removed, or unexplained loss. These
are expected contracts, not results recorded by this design.

P is a direct single-parent child of S. Relative to S, its maximum path


P performs exactly these authority changes:

   `HISTORICAL_ACCEPTED` without changing its artifact;
4. switch the one registry selector to the new active record;
5. replace the one literal workflow profile token with the same exact ID.

P does not modify verifier logic, add a fallback, edit an old artifact, run a
dynamic registration step, or record E/review/CI/D2 facts. The materializer's
canonical data preimages, not JavaScript source bytes, prove the append.

## 12. Historical preservation audit

At S, moving the embedded artifacts is a mechanical relocation. Review must
verify that every deleted historical artifact span from the design-base
verifier has one byte-identical added artifact span in the module, in the same
order. The selected 2B20A span remains exactly 2930 bytes with the frozen SHA.
This is a one-time Git-diff custody audit, not executable parser logic and not a
runtime authority path.

At P, the historical artifact array prefix is byte-identical to S and exactly
one object is appended. Metadata status/selector changes do not change
historical artifact bytes. An old-profile byte difference is a closed failure;
the artifact is never reconstructed from newer state.
