## 8. Final three-authority model

### 8.1 P profile-artifact authority

The new standalone P JSON file is the sole authority for the new profile's
complete data: profile identity, source HEAD, source/test counts, inventory
and tuple identities, topology, obligations, and canonical profile-body SHA.
The temporary S candidate is not authority. Registry metadata cannot modify or
replace the artifact. E cannot copy the full artifact or become its source.

The 17 legacy profile objects remain immutable historical artifact authorities
in the existing verifier. They are resolved as already-loaded data by exact
ID; they are never recovered from source text.

### 8.2 Metadata-only registry authority

`scripts/coverage-profile-registry.mjs` owns only identity, lifecycle/selection
status, source/test counts, inventory/tuple hashes when known, artifact path,
coverage group counts when known, predecessor, source/test deltas, loss, and
one exact selector mapping. It contains no topology body, obligations body,
coverage output, profile body, artifact bytes, artifact file SHA, callback,
filesystem operation, Git operation, environment access, dynamic registration,
or BOTC runtime value.

### 8.3 E hash-evidence authority

E owns only direct P/registry/artifact hashes, immutable migration preimages,
tuple summary, transition facts, S/P ancestry facts, lifecycle classification,
and offline review instructions. It cannot generate, select, load for runtime,
modify, replace, reinterpret, or accept a profile. It is never a D2 product or
profile input.

### 8.4 Non-interchangeability

If the artifact and registry conflict, validation fails; neither silently wins.
E describes the already-existing P state and cannot repair a conflict. A hash
proves byte identity only. The presence of an `ACTIVE` registry status means
selected for this coverage verifier; it does not mean PR acceptance, product
acceptance, BOTC correctness, or role completeness.

## 12. Verifier direct-import and single-resolution contract

`scripts/verify-coverage-obligations.mjs` directly imports the four registry
exports. It never reads registry or verifier source text. Validation order is:

1. export/schema presence and module purity census;
2. dense recursively frozen data, exact keys and order;
3. unique profile IDs and closed lifecycle domain;
4. exact 17-row S or 18-row P transition shape;
5. canonical IDs, OIDs, hashes, counts, nullability, paths, predecessors,
   deltas, and zero-loss domain;

7. exact requested profile equals selector mapping;

9. validate artifact closed schema and canonical profile-body SHA;

    artifact;

    obligations.

repository-relative path. This is one closed resolver dispatch over distinct
record states, not two alternative authority paths. No record may be resolved
both ways; no compatibility or fallback branch exists.

symlink/junction, non-file, missing file, wrong ID/source/schema/hash/count,
